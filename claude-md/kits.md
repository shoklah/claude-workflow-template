# Kits

A kit specializes the workflow for a topic, only on the work that needs it. It adds to stages; it never changes the path, the models, the caps or the order of steps. Read this file when the project's `CLAUDE.md` names a kit under `## Kits` or a plan task carries `**Kit:**`. Nothing here applies to the Direct path.

- **Lookup:** `/usr/bin/python3 -I ~/.claude/scripts/kit.py show <name> [--stack <stack>]` prints the kit's manifest with full paths: `applies_when`, `design`, `guidance`, `checklist`, `checks` and `bindings`. Use the paths it prints and never one of your own. If it refuses, say why and leave that kit's work until the owner answers.
- **The project:** its `CLAUDE.md` has a `## Kits` section with one line per kit, `- <name>` or `- <name> [<stack>]`, followed by what the kit's `design` file asks a project to state (for a kit that looks at pages: the command that serves invented data, which takes a port, and its base URL), each indented under the kit's line as a sub-item:
  ```
  - ui
    - serve: ...
    - base-url: ...
  ```
- **Design:** in a project that names a kit, read the kit's `design` file before the first design question. It lists the kit's prerequisites, the points the spec must settle and the things the design must produce for the owner to approve. On the Small path this happens before the first task. A missing prerequisite is said in one line and built first, with the owner where it needs them; one out of date is updated and said in one line.
- **Plan:** mark every task the kit's `applies_when` sentence fits with `**Kit:** <name>` (`**Kit:** <name> [<stack>]` where the project names a stack), adding `; tags: <tag>, <tag>` for each binding tag the task calls for, and the lines the `design` file asks of a task. A task that fits but is trivial carries `**Kit:** exempt: <reason>` instead. Show the owner one line at plan approval, such as `Kits: ui on tasks 3 and 5`. On the Small path, name the kit in the first message beside the path.
- **Brief:** a kit task's implementer brief names, as files to read in full before writing anything, the kit's `guidance` and every binding with no tag or with a tag the task carries. On the Small path the session reads them itself.
- **Checks:** after a kit task's tests pass, the session running implementation runs each of the kit's `checks` commands from the task's worktree, or the folder under it that the kit's `design` file has the project name, adding the arguments the `design` file names and an output folder `~/.claude/workflow-archive/<the ledger's name without .md>-kit/task-<N>` (`branch` in place of `task-<N>` on the Small path). Exit 0 is passed, 1 failed, 3 could not run. A failed check goes back to the implementer as a failed check, under the cap for checks: it is never a review finding. A failure the branch did not cause is not the implementer's: when a check fails, the session runs it once more on the task's start SHA (the branch's start on the Small path), from a temporary worktree of it with the project's ignored folders linked, served the same way, into the output folder with `-base` added, then removes that worktree. A failure the base has too, same check, screen and width, goes in one ledger line, `Kit: task <N> base also fails (<check>, <screen>, <width>)`, and on the owner's finish list with both details instead of back to the implementer; the other failures go back as usual, and a check whose every failure the base has too counts as passed for **Review** and **Record**. Where the checks need a served page, the session starts the project's serve command itself, from the task's worktree and on a free port, before the checks, and stops it after the kit review; implementers and reviewers start no server.
- **Not verified:** when a check could not run, try once more (on another port where one is used). If it still can't, write `Kit: task <N> not verified (<why>)` in the ledger and carry on with the run.
- **Review:** once the kit's checks pass, dispatch `kit-reviewer` in the same message as `task-reviewer`, with the kit's name, its `checklist` path, the task brief, the output folder and what the checklist needs. Its findings join the task's fix round under the one cap of three. `fix-checker` re-checks `task-reviewer`'s findings as always; the kit's findings are re-checked by `kit-reviewer`, in a dispatch whose description starts with `Re-check` and which lists only those findings. Ledger lines for kit findings name the step `kit_review`, the category `kit` and the finding's label.
- **Waves:** in a wave, each kit task's checks run after the wave is merged, from the session's worktree with that task's lines, and each kit task gets its own `kit-reviewer` dispatch in the same message as the wave check, its step carrying that `task`.
- **A kit finding never stops a run:** one still open after round 3 gets a written ruling, the run continues and the finding goes on the owner's finish list. The stop rule still applies to every other finding.
- **Small path:** before the first task, the session does what **Design** says, then shows the owner the points the `design` file asks a spec to settle and the things it asks the design to produce, and the owner approves them before the task's work starts. The approved points go in one ledger line, and the approved artifacts are kept in an `approved` folder inside the branch's output folder (see **Checks**) for `kit-reviewer`. After `simplify` and the checks, run the kit's checks once over the branch, then dispatch `kit-reviewer` once in the same message as `final-reviewer`. Its findings join the final review's one fix wave. If the branch's checks still can't run after the retry, write `Kit: branch not verified (<why>)` in the ledger, still run `kit-reviewer` on whatever the checks left (or on the branch with no screenshots, saying so), and say so at the top of the finish, offering no pull request until the owner says to.
- **Catch-up (Full):** after `simplify`, for every task left not verified, run the kit's checks and one `kit-reviewer` pass on the branch's final state. If that can't run either, say so at the top of the finish and offer no pull request until the owner says to.
- **Finish:** list each kit task's output folder for the owner to look at, then every kit finding left open with its ruling and every check failure the base also had. A result the owner approves there may be worth adding to the kit's library: suggest it, and copy nothing without their yes.
- **Record:** the run record names each kit in `kits` with its version, its tasks and the files the briefs named, each kit task's last check result in `kit_checks`, and each `kit-reviewer` dispatch as a `kit_review` step, or a `fix_check` step for a re-check, or a `final_fix_check` step once the final review has launched, carrying `kit`; the catch-up's `kit_review` step carries no `task` and covers every task of its kit; a kit finding's `category` is `kit` and its `label` the checklist line's name. `--schema` prints the format.
