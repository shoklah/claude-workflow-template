# Agentic workflow
This section outranks the skills and redirects them without editing them.

- **Path:** in your first message name the path and why, the Fable stage and the recommended model; the owner may override. **Direct** (typos, docs, comments): the edit plus any automated checks. **Small** (clear request, about 1 to 3 files, outside the risk areas): implement in the session, `simplify`, automated checks, one fresh `final-reviewer`. **Full** (everything else): the pipeline below. Risk areas always take Full: authentication and permissions, payments, data migrations or deletions, production infrastructure, concurrency, public API changes. If the session's model differs from the recommended one, say so and carry on. If a task grows past its path, stop, say so and step up.
- **Fable stage:** at task start read `get_usage` (`mcp__ccd_session_mgmt__get_usage`). Share of the week gone = `100 * (168 - hours_to_reset) / 168`; compare the weekly Fable % with it.

| Stage | Trigger | Other main sessions | Design and plan | Plan review | Final review |
|---|---|---|---|---|---|
| 1 | Up to 15 points ahead of the week | Owner's choice, Fable allowed | Fable | Fable | Fable |
| 2 | More than 15 points ahead | Opus 5.5 with Fable advisor | Fable | Fable | Fable |
| 3 | 90% used or more | Opus 5.5, advisor off | Opus 5.5 | Opus 5.5 | Fable |
| Out | Fable unavailable | Opus 5.5 | Opus 5.5 | Opus 5.5 | Opus 5.5 at `xhigh` |

- "Other main sessions" means sessions outside the pipeline's fixed roles, such as Small path work. The session running implementation is Opus 5.5 at `medium` in every stage. The advisor is on in stages 1 and 2 and off from stage 3; when the stage calls for a change, remind the owner to type `/advisor fable` or `/advisor off` (only they can). Also read the all-model %: warn when it is more than 15 points ahead of the week, and at 90% start no new Full path run without the owner's OK. Nothing silently drops to Sonnet.
- **Agents:** these replace the skills' `general-purpose` dispatches. Implementer: `implementer`, or `implementer-copy` only when the plan's text holds the function bodies, not just signatures and tests. Plan simplify: `plan-simplifier`. Plan review: `plan-reviewer`. Task review: `task-reviewer`. Re-check of listed findings: `fix-checker`. Final review and the Small path's reviewer: `final-reviewer`. Frontmatter pins model and effort: pass `model` only for a stage 3 or Out override, and `effort: xhigh` for `final-reviewer` in risk areas. Any skill that fans out `general-purpose` agents without a model (`simplify`'s four agents, `code-review`) passes `model: opus` and `effort: high` on each dispatch. If a named agent is "not found", stop and ask the owner to restart the session; never fall back to `general-purpose`.
- **Plan review (Full):** the planning session keeps its own ledger from its first message, as under Run record, in `~/.claude/workflow-archive/<date>-<branch>-plan.md`. After the owner approves the design, it dispatches `plan-simplifier` and applies its findings itself, cutting what the spec doesn't require too, then a fresh `plan-reviewer`; each gets the spec, the plan and the repo, not the brainstorm. One pass each; the review's findings go back to the planning session, then the owner approves the plan and sees with it, one line each, every cut, every declined finding with its reason, and the spec flags; right after that approval, it appends a `path: "plan"` record with its steps, in the format `--schema` prints. The dispatch hook refuses a plan review until a plan simplify has launched since the last plan review. Then offer to start the implementation session on Opus 5.5 at `medium` through `start_session` with explicit model and effort; it starts from the plan's path only and uses `subagent-driven-development`.
- **TDD and checks:** TDD is the default on the Small and Full paths, main sessions on the Small path included. After each task the session running implementation runs the tests, type checks, build and `/usr/bin/python3 -I ~/.claude/scripts/failing-test-check.py --base <task start SHA> -- <command>` itself, not trusting the report, from the worktree or with `--repo <worktree>`. Pass `--link <path>` for each ignored folder the tests need (`node_modules`, `.venv`) and `--test-file <path>` when detection misses the task's tests. The command runs only the task's new or changed test files, never a whole suite (an unrelated failure at the base would make a false pass); run it in the background or with a `--timeout` whose double fits inside the Bash tool's limit, since it applies to each of the two runs. `failed`, or `no_tests` on a task that isn't exempt, goes back to the implementer as a failed check; "couldn't run" (`couldnt_run`) is reported without blocking. A plan marks a task with no new behavior (refactor, docs, config) with `**Failing-test check:** exempt: <reason>` in its header, and that task skips the check.
- **Caps:** failing automated checks get 3 attempts, then one fresh attempt one tier up, then stop and ask the owner. Review fixes get at most 3 rounds per task: rounds 1 and 2, the original implementer fixes the open findings and `fix-checker` checks only those; round 3, a fresh implementer one tier up (`implementer-copy` to `implementer`, `implementer` to `implementer-escalated`, but in stage 3 a fresh `implementer`). A finding that comes back unchanged skips straight to round 3. **Stop rule:** after round 3, a real Critical or Important finding still open stops the run and asks the owner; one where the reviewer may be wrong gets a written ruling, the run continues and the final review sees both sides. Minor findings go in the ledger and never enter the loop. `fix-checker`'s "fixed, not proportionate" counts as open within the cap; at round 3 it gets a written ruling, not a stop, and after the final review's fix wave it goes on the owner's list.
- **Simplify and final review:** once all tasks are done, run `simplify` once over the branch (and on the Small path), then the automated checks again, then `final-reviewer`; the dispatch hook refuses it until `simplify` has run. The session applies `simplify`'s fixes itself, as a stated exception to the skill's "never fix in the controller", because the final review follows straight away. The final review gets one fix wave and one `fix-checker` re-check, and the stop rule applies there too. Its list of what the spec doesn't require goes to the owner, not to fix rounds.
- **Waves (Full):** the planning session may mark `**Wave:** A` on consecutive tasks that change no same part of a file (a file two tasks share appears in both `Files:` blocks with the part each changes), use nothing a sibling adds and have tests independent of their siblings, at most 3 per wave; `plan-reviewer` checks each wave. The session running implementation records the base (`git rev-parse HEAD`), runs `/usr/bin/python3 -I ~/.claude/scripts/wave.py start --base <sha> --link <path>... <tasks>` with the project's `--link` paths, appends `Wave A: started (tasks 3, 4; base <sha7>)` to the ledger and dispatches each implementer with its task worktree as working directory, saying every command starts there; every per-task step runs as today, with `--repo <task worktree>` for the failing-test check, `-C <task worktree>` for the SDD scripts, and the wave base as the task's start SHA. When every task in the wave is complete, it runs `wave.py merge <tasks>` in plan order: a conflict that is two additions to one list or section it resolves, keeping both, and commits; any other gets a ruling in the ledger and one `implementer` to finish that merge; either way, it then runs `wave.py merge` for the tasks left. It folds the reports' `Conventions:` lines into `## Code conventions` and commits, runs `wave.py finish <tasks>`, runs the automated checks and appends `Wave A: merged (<sha7>; conflicts: none)`, or the conflicting task and files. Then one `task-reviewer` reviews the wave's whole diff, from its base to the merged head, with the wave's briefs as the wave check, its dispatch naming the conventions just folded in; its findings get a task's fix rounds on the run branch in the session's worktree, by one `implementer` resumed in round 2 (round 3 as under Caps), whose reports' `Conventions:` lines are folded in the same way, and the session appends `Wave A: complete (<base7>..<head7>)`. A stop in one task lets the others finish their current round and merges nothing. After compaction, a `started` wave with no `merged` line resumes each task in its worktree from its last ledger line, and a `merged` one with no `complete` line resumes at the wave check or at its last fix-round line. Finding lines name the wave where they would name the task; the record's `waves` lists each wave with its tasks and conflicts, and the wave check and its fix-checks are steps carrying `wave` in place of `task`; a wave's review and fix-check steps go in the record in the order their dispatches launched.
- **Five rules,** for plans, code and fixes, outranking the skills' templates where those ask for more structure. **Simplest first:** the smallest direct change. **Reuse before writing:** use or extend an existing function, helper or pattern, never a parallel version. **Match the codebase:** its style, logic and abstractions and the project's `## Code conventions`; no structure it doesn't have. **No pattern yet:** take the simplest way; an alternative goes to the owner as a suggestion, unbuilt. **Decisions live in the project's `CLAUDE.md`:** one line each under `## Code conventions` in its root `CLAUDE.md`, stating the rule, not its history. The design session records what a design settles, the implementer a rule-4 pattern or a relied-on convention not yet recorded, and the session running implementation a ruling about code shape.
- **Finding bar:** a "this can break" finding is Critical or Important only with a shown path in this code; inside a risk area, plausibility is enough, and a shown path makes it at least Important, even if it looks rare or benign. Judge it per finding, by the code it concerns; test code isn't a risk area. A finding naming the existing helper or pattern a change duplicates, bypasses or departs from is Important, and so is a missing or contradicted `## Code conventions` entry.
- **Guidelines:** `karpathy-guidelines`' "if uncertain, ask" and "offer better approaches, even mid-task" apply only when the answer would change what gets built. Inside a running plan, implementers report `NEEDS_CONTEXT` rather than stopping to chat and put suggestions in their report. "Loop until verified" is subject to the caps above.
- **Advisor:** implementers only when stuck on a recurring failure or before departing from the plan; the session running implementation and other Opus main sessions at their own judgment; reviewers, `fix-checker` and sessions already on Fable never. Right after any consultation, write one line in your reply text: `Advisor: <what it advised> | changed: yes or no | <what changed>`. Implementers also carry it into their report file.
- **Offers:** offer a skill, never start it: one question with yes/skip buttons, and run it only on yes; a skip means "not now", so the offer comes back at its next moment. Offer `grill-me` on every Full design, once, right before the owner approves it. Log each offer in the ledger, and record `grill-me` in the plan record's `offers`.
- **Run record:** keep the run's ledger from your first message: on a Full run the SDD ledger, on a Small run a file `~/.claude/workflow-archive/<date>-<branch>.md` (`/` in the branch replaced, a suffix if the name is taken, `mkdir -p` on first use). Give it a `Started: <ISO time>` line, the time of your first message, and after each review, fix-check, `simplify`, plan simplify and plan review one line per finding (`F1`, `F2`… with step, task, round, severity, category, summary, outcome and validity) and one per strength (`S1`, `S2`… with step, task, round, category and summary), then a line by number whenever an outcome or validity changes. The category is the reviewer's; pick one from `--schema`'s `category_list` only when the report gives none or one off its area's list, and for `simplify`. Validity is your call, by the definitions there: valid when the problem is real, even outside the brief. Before the SDD workspace is deleted, copy `progress.md` to the archive under the same naming. When a Small or Full path run finishes, before the ledger is deleted, append one JSON line to `~/.claude/workflow-log.jsonl` in the format `/usr/bin/python3 -I ~/.claude/scripts/workflow-report.py --schema` prints, filling `schema`, `started`, `plan`, `archive`, `categories`, `steps` and `offers` from the ledger, each step's `counts` leaving out `strengths`, each dispatched step's `agent_id` being the id the Agent tool returned, which every dispatch line in the ledger names (`agent <id>`), and `simplify.ran` and `fix_growth`. Write it as one literal line in a quoted heredoc (`cat >> ~/.claude/workflow-log.jsonl <<'EOF'`), never a script or shell variables: the report finds the run's session by the `started` and `head` values in that command. Then run `/usr/bin/python3 -I ~/.claude/scripts/workflow-report.py --brief` and pass any `STOP`, `CHECKPOINT` or `WARN` line on to the owner, along with the run's rulings at finish. Run `/usr/bin/python3 -I ~/.claude/scripts/workflow-report.py --health` at the trial checkpoint and whenever the owner asks.
